# V0.3.8 Match History — local review checkpoint

Based on final V0.3.7 commit `d815b999c73caafe5fc907cc6a46524612dd5273`.
Develop/test/build locally. Do not push this branch or trigger Netlify until
physical iPad testing is explicitly requested. Frozen release refs are unchanged.

## Storage and schemas

The active match remains in `localStorage['sideline.match.v1']`, using match
payload schema 2 and the same event log. Squad templates and the legacy backup
keep their existing keys. History uses IndexedDB database `sideline.history`,
database version 1, object store `matches` keyed by match ID. Each envelope has
`repositoryVersion: 1`, a validated match payload, origin, and an archive timestamp
when actually known. The repository schema is independent of the match schema.

Optional `match.lifecycle` records explicit completion status/time, creation or
resume time. End Match pauses the clock and records completion without inventing
events. Existing event-based calculations and pitch coordinates are unchanged.
Legacy records without reliable completion metadata are labelled Archived; no
final result or completion status is inferred from a paused clock or a score.

## Discovery and non-destructive migration

Opening History enumerates `sideline.match.archive.<match-id>` keys, validates and
migrates each payload in memory through the existing match migrator, and copies
valid records into IndexedDB. Discovery never edits/removes the original archive,
active key, squad templates, or backup. Repeated discovery uses the same IDs.
Corrupt or unsupported records produce recovery warnings and retain their source
bytes. An IndexedDB outage still permits browsing readable localStorage archives.
Records stored only in inaccessible IndexedDB cannot be displayed during an outage;
this is reported, not presented as an empty successful history.

New archives prefer IndexedDB; localStorage recovery snapshots remain a fail-safe
if IndexedDB cannot write. Archive transaction completion is awaited before writing
a replacement active match. Failure of both stores prevents New Match/Resume.
If the active match changes while the archive write is pending, replacement is
aborted. A failed active write leaves the old active record and archived copy
recoverable. This orders two different browser stores safely; it is not a claim
of atomicity across localStorage and IndexedDB.

## Read-only viewing, resume, deletion

Historical viewing uses a separate cloned payload and does not replace, pause,
autosave or otherwise mutate the active match. Existing Full-Time/Half-Time
calculators, detailed analysis, timeline and `src/pitch.js` are reused. No second
statistics engine exists. Mutating match controls are absent and historical
buttons are handled separately from touch capture. Printing uses the existing
browser Print / Save as PDF report, subject to device/browser capabilities.

A running clock saved by V0.3.7 has no reliable archive-stop timestamp. Historical
viewing freezes it at the larger of its saved elapsed time and latest recorded
event time in that half; wall-clock time since the old start is never added.
New archives freeze the clock at their known archive time. These are copies;
original legacy bytes and event times remain intact.

Resume is a separate confirmed action for non-completed records. It archives the
current match first, restores the selected match with the same ID, and leaves the
clock paused. Completed records are read-only in History. The active match is
pinned separately in the list; its duplicate archived ID is hidden.

Delete requires confirmation, refuses the active ID, and removes only that
historical payload and its matching localStorage recovery source. A small ID-only
tombstone prevents discovery from resurrecting a deliberately deleted legacy key.
Deletion requires writable IndexedDB. Before removing a legacy source there must
be a validated durable copy; if the subsequent transaction fails, that copy remains
recoverable. Current match, saved squads and other archives are never deleted.

## Presentation and limits

Archived cards sort newest first by reliable completion/match/start timestamps;
undated records remain listed. The current match is pinned. Search matches team
names only. Cards show event-derived Gaelic score, competition/date and lifecycle
status; final WIN/LOSS/DRAW is shown only with explicit reliable completion data.
Unknown legacy status stays neutral. Missing event details/locations remain missing.
Original OCR photographs are not retrospectively recovered from match payloads.

This checkpoint is offline/local-device only, not a permanent backup. Browser
storage clearing/eviction, private-mode restrictions and device loss remain risks.
IndexedDB use does not turn local storage into cross-device synchronisation.

## Future backup/restore boundary

A future export can enumerate validated repository envelopes, include a format
manifest plus match/repository versions and checksums, and download one offline
backup. Restore must validate every payload, preview duplicate-ID conflicts,
confirm replacement decisions, and commit transactionally without clearing the
active match or originals first. Schema migrations should be independent and
repeat-safe. Full backup/restore is not implemented in this checkpoint.

## Regression provenance

`tests/fixtures/History_V037_Archive.json` was generated with the frozen V0.3.7
domain/event code, not the History repository. It includes both halves, goals,
points/two-pointers, an attacking blocked shot, a defensive block, kickouts/Mark,
player credit, shot coordinates and a legacy running clock without archive metadata.
Browser tests seed its exact JSON into V0.3.7 localStorage keys before opening
V0.3.8 and verify discovery, shared analyses, exact SVG positions, unchanged active
and legacy bytes, repeat-safe copying, confirmations, failure recovery and offline
reload. Source fixture names are test data only, never application defaults.

Rolling back to V0.3.7 can still open the active localStorage payload and its
original recovery keys; that version has no UI for native IndexedDB archives.
Those records remain on the device and reappear when V0.3.8 is used again.
Reopening Full-Time Analysis does not rewrite an existing completion timestamp.
