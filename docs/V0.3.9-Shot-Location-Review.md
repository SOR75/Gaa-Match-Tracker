# V0.3.9 shot-location / 40m audit and correction — uncommitted

## Audit before correction

1. `shot-capture.js` reads the selected event team and half, obtains `attackingDirection(match, event.team, event.half)`, and applies the inverse 180-degree transform when saving a pitch tap. Therefore **stored shotX/shotY already face that team's attacking goal at TOP**, in both halves and for both teams. Live capture deliberately faces the physical attacking end; that display changes with half/team/setup. Historical coordinate editing also explicitly describes attacking-top coordinates. This is the established V2/V3 convention, not newly introduced storage.
2. Detailed Match Analysis, printed Match Report and Full-Time already pass canonical coordinates to the shared pitch at TOP. They do NOT combine unnormalised physical H1/H2 coordinates. Flipping every stored H2 event would introduce errors.
3. Half-Time was different: it applied our physical first-half attacking direction again. With first-half Bottom configured it rotated canonical coordinates back to the bottom, while Full-Time/report showed top. That confirmed inconsistency is corrected. H1 Top presentation is unchanged.
4. Archive 3 contains four original PNG screenshots, not event exports. The H1 images show top-oriented maps; the Full Match images add a few far-end markers rather than a second cluster for every H2 event. These confirm the observation but **do not establish the cause of individual Full Match outliers**. A wrongly placed tap, wrong attribution or a genuine long attempt cannot be distinguished without the saved events. No screenshot-derived event coordinates, team/half assumptions or corrective flips have been invented.

## Pre-fix 40m calculation

The geometry already shared a 600×900 viewBox, goal centre (300,20), and radius 240 SVG units (6 units per nominal metre, following the existing 45m-line scale). The old classifier was:

`y <= 145 + epsilon OR distance((x,y),(300,20)) <= 240 + epsilon`

It was not merely a horizontal threshold, but it included the entire width goal-side of the 20m drawing line, even where circular distance exceeded 40m. The drawn circular paths stopped at that line, at x≈95.122 and 504.878. The circular segment used the same radius; its full boundary semantics were not the requested pure circular inside/outside rule. Exactly on the arc counted inside. Event type was not checked, so an inside-coordinate two-pointer could be counted inside.

## Correction

- All current analysis entry points use attacking TOP. Half-Time no longer applies physical orientation a second time. Capture and `transformLocation` are unchanged. Both-team/H1/H2 normalisation still happens correctly at capture; analysis consumes those canonical coordinates without another flip.
- The 40m paths are now complete semicircles centred on each goal line, sharing the existing radius/scale with classification: top `M60 20A240 240 0 0 0 540 20`; bottom `M60 880A240 240 0 0 1 540 880`. This extends the former truncated arcs into the goal-side wings; it does not change pitch dimensions, other markings, event coordinates or tap mapping.
- A usable point is inside iff its centre is strictly within the 240-unit circle. On/beyond the circle is outside. Floating-boundary tolerance is only 0.000001 SVG unit. The full-width horizontal exception is removed. Classification uses marker centres, not the outer edge of marker glyphs.
- Coordinates outside the marked field, missing coordinates and inconsistent inside-arc two-point locations are unclassifiable. Original marker positions remain visible when located; they are not moved to satisfy a rule.
- Shared `shotLocationAnalysis` provides the same location buckets for H1/H2/Full Match dashboards, detailed statistics, printable Match Report and History. Team filtering uses each team's already canonical shots independently. Existing map filters remain map-only; the location table follows the same whole-match/H1/H2 analysis scope as the surrounding report statistics.
- Conversion is successful attempts divided by attempts in that classifiable bucket. A goal and a two-pointer each count as one successful attempt, not three/two percentage units. Unknown/unlocated attempts stay in overall shooting and do not enter either bucket.

## Two-pointer safety

Existing capture permits recording an inside-arc two-pointer, or a two-pointer without location. Capture remains immediate and non-blocking; no new confirmation or rule enforcement screen is added. A valid outside-location two-pointer enters Outside 40m. An inside-location two-pointer now remains one scored event, keeps its original coordinates and score, and is placed in the unknown location bucket with an explicit review message. It is never silently classified Inside or moved/invented Outside. An unlocated two-pointer remains unknown. The same explanation appears in the detailed/report location analysis.

## Data protection and real-match limitation

Unit and browser tests compare original event arrays across analysis, completion, report and offline History.
