## Update policy

- Online document navigations use a fresh network request that bypasses the HTTP cache, with a four-second timeout and cached fallback on failure.
- A network-fetched newer document never overwrites the active worker's fully precached offline document. This retains a coherent fallback if the newer install fails or the network disappears mid-update.
- Hashed assets remain cache-first. Already-installed waiting workers' immutable hashed chunks may also be used offline.
- New workers precache their full shell using HTTP-cache-bypassing requests. A failed install does not activate or remove the previous usable shell.
- Worker scripts, application HTML and build metadata have explicit Netlify no-store/revalidation headers. Build metadata is also network-first with an offline snapshot fallback.
- Registration uses `updateViaCache: none` and explicit update checks on opening and network reconnection.
- Update discovery displays the existing non-blocking update notice. There is **no forced reload, skipWaiting or clients.claim**. An existing live recording continues with its current JavaScript and clock.
- A waiting worker activates after the old clients close. Only old `sideline-*` application caches are then retired; neither Local Storage nor IndexedDB is accessed by update code.

## One-time bootstrap for the old cache-first worker

An already-installed legacy worker cannot gain a new fetch strategy until the updated worker is installed and activated. After the branch deployment is ready:

1. While online and outside active match capture, open the same Sideline hostname with a unique query, for example `/?sideline-update=<new-commit-SHA>`, in the browser/PWA context holding the saved matches. This is the same origin and does not change or replace the current match. The legacy worker's exact cached `/` URL does not match that new query, so it retrieves the current online HTML.
2. Confirm **V0.3.9.3**. Let caching complete and wait for the update-ready notice if an older worker still controls the page.
3. Close all Sideline clients on that origin, including other tabs/windows/Home Screen clients. Reopen the normal URL. The fully cached new worker can now activate. Future online openings use the new network-first strategy.
4. Confirm the visible version and inspect `window.__SIDELINE_BUILD__` if technical source identification is needed.

Never use Clear site data, delete browser databases, reinstall the app, or create/re-enter either real match as an update procedure. Other hostnames or browser/PWA contexts may have separate storage. If the network is unavailable, the last fully cached application remains available; an offline device cannot discover a deployment it has not downloaded.
