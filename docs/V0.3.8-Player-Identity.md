# V0.3.8 permanent player identity foundation

Local development checkpoint based on Match History commit `105f5b63c4db4ee1194556cd9fec604135ea6cde`. No cloud, profiles, season management or historical linking UI.

## Saved Squad

`sideline.squads.v2` contains `{version: 2, squads: [...]}`. Squad `id` is its stable squadId, with nullable `clubId` and `seasonId`. A player has a permanent UUID v4 in `playerId` (`id` is its library-row alias), name, optional default number, preferred position (`position`), secondaryPosition, role, notes and status (default active). Permanent IDs are generated at Squad creation, never by validation or copying. The same playerId can belong to more than one squad. No names or jerseys are uniqueness keys; two players with identical names remain distinct.

The first read copies the old v1 library to v2 without overwriting v1. A unique valid UUID already stored as a v1 row ID is retained; missing/non-UUID/repeated IDs receive separate UUIDs. Generated IDs are not exposed until v2 is durably written. Malformed storage or a failed write blocks library mutation, retaining the original for recovery. This establishes library identities only: old match players/events are not automatically linked even if their old IDs, numbers or names resemble the library.

Saving an ad-hoc match roster as a Squad establishes identities in the library; it does not retroactively link that match. Loading the Saved Squad is an explicit prospective association. Separately creating another Saved Squad from unlinked rows creates separate people; no automatic person deduplication is attempted.

## Match roster and provenance

The existing schema-2 whole-match payload remains in use. New roster entries add `matchPlayerId` (alias of the existing local `id`), `playerId|null`, `nameSnapshot`, `jerseyNumber` (alias of `number`) and `sourceSquadId|null`. `name`, `number`, `position`, `role` and notes remain the match-specific snapshot. Saved Squad loading retains match `squadId`, nullable `seasonId` and `oppositionSquadId`; each loaded row also carries sourceSquadId. Across matches, matchPlayerId differs while playerId stays the same. Re-loading the same player into the same existing roster preserves its matchPlayerId.

Manual/imported rosters remain supported with playerId null. Validation does not manufacture identity. Historical payloads retain their own roster, not live pointers into the Saved Squad library; editing the library cannot rewrite history.

## Events

New events add `identityVersion: 1` and nullable `participants` entries for `player`, `markWinner`, `blocker`, `playerOn`, `playerOff`. Each reference contains team, matchPlayerId, nullable playerId, nameSnapshot and jerseyNumber at attribution time. Number fields remain unchanged for readable history and backwards compatibility. Initial number-based UI selection binds to a single unambiguous roster row at capture time. No additional UI/taps are introduced.

Edits to notes/location/outcome that retain an attribution preserve the reference; explicit changed/cleared player attribution rebinds/clears it. The saved reference cannot drift to somebody else who later wears that jersey. Missing roster entries resolve to the reference's recorded snapshot, never another same-number/same-name person. Mark and blocker references are our-team references independently of the kickout/shooting team. Substitution on/off references are separate.

Analysis groups new attributed events by team and matchPlayerId, exposes playerId for future cross-match aggregation, and retains all existing statistical definitions. Cross-match profiles are not implemented. Shot filters and substitution on-field resolution use the stable reference. Legacy/unlinked number groups remain separate from linked groups, explicitly labelled where the same jersey is present in a linked roster.

## Legacy and History

Legacy events without identityVersion remain number-only, including when edited, loaded into History or resumed. New fallback-number events captured without a roster remain unlinked if a roster is later added; names can still display via the existing number fallback. No historical association by name, number or array position is performed.

No IndexedDB version/store, repository envelope or Match History UI change is required: the existing repository stores and clones the full schema-2 payload including additive fields. Active-match localStorage, archive migration, read-only History, Resume, Delete and failure recovery remain unchanged. Existing legacy originals are not rewritten by library upgrade. A future explicit coach-confirmed linking feature must retain original evidence and must not silently merge old rows.

## Limits and follow-up

IDs are local UUIDs using crypto.randomUUID, with the existing cryptographic getRandomValues fallback. They do not provide backup: clearing browser data still loses device-local data. v1 is a recovery copy, not a synchronised dual-write library; the frozen V0.3.7 build will not see new v2 Squad edits. New identity-aware payloads should be handled by V0.3.8 or later to retain identity semantics.

No global player directory exists yet. Separate ad-hoc Squad creation can represent the same person with different UUIDs; an explicit linking/reconciliation workflow is future work. OCR never guesses permanent identity. Stable club/season ownership, memberships, profiles, cross-match statistics and sync conflict policies remain future work; nullable metadata and UUIDs allow those additions without using jersey/name keys.


The subsequent local Player Review refinement uses the official name-only Squad template. The live Saved Squad load explicitly leaves new match jerseys blank and roles unselected; it never auto-applies old library defaults. Stable playerId and existing historical snapshots remain unchanged. See V0.3.8-Player-Review-Refinement.md for participation evidence and current on-field reconstruction.
